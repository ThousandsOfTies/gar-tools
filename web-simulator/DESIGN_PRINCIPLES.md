# GAR Webシミュレータの設計方針

この文書は、GARのWebシミュレータに対するユーザーの期待と、実装・レビュー時の判断基準です。
すべてのGAR App／Product／Targetに適用します。新規作成、機能追加、見た目の変更の前に読み、
既存の[Agent向け実装指示](../AGENTS.md)と[部品のAPI・利用手順](README.md)に従って作業します。

## 求める「ちょうどよさ」

**実機につながるアプリの動作を、部品に触れる感覚で軽く試しながら、
作る・試す・直すを途切れずに回せること。**

特に大切なのは、**「生の部品感」を残すこと**です。ディスプレイ、ボタン、ノブ、センサー、
サーボが、それぞれ何の部品で、何ができるのか分かる姿で存在していることを求めます。
その姿から「これを別のアプリでも使えそう」「この部品を組み合わせたら何ができるだろう」
という発想が生まれることも、シミュレータの価値です。

コードとして再利用できることに加えて、**見た目から再利用を思いつけること**を品質の条件にします。
部品単体のサンプルと実際のProductパネルの両方で、この性質を保ちます。

## 設計の原則

1. **部品そのものが見える。**
   ノブなら回転と押下、サーボなら軸と角度、ディスプレイなら画面の範囲と解像度が分かる姿にします。
   形状、可動部、端子、チャンネル、単位などから、操作と理解に必要な手掛かりを選んで残します。
   見た目の作り込みは部品の認識と操作を助けるために行い、細かさは検証目的に合わせます。
   部品らしい姿と、マウス・キーボードでの操作のしやすさを両立させます。
   ノブは目盛りや指標の回転を見せつつ、−／＋、矢印キー、フォーカス中のホイールなどで操作できます。
   円周をなぞるドラッグのような実物に忠実なジェスチャーを必須にせず、押下も独立して扱いやすくします。

2. **アプリの意味はProduct側で組み立てる。**
   アプリらしさは、ディスプレイ内の表示、部品の配置、外側のラベル、動作の割り当てで表現します。
   たとえば同じノブを音量にもメニュー選択にも使える姿とAPIにします。
   Product全体のアニメーションや説明図を加える場合も、部品の姿と基本操作を把握できる構成にします。

3. **再利用する部品はgar-toolsのWeb Componentとして作る。**
   まず`web-simulator/components/`の既存部品を確認し、適切なものを再利用・拡張します。
   共通部品は見た目、局所的な操作、物理・設定上の性質を公開APIとして持ちます。
   配線、校正値、Productのメッセージ解釈、コマンド、シナリオ、接続先の選択はProductのadapterに置きます。
   Productページは部品タグを組み合わせ、内部DOMやスタイルをコピーしたり外から参照したりしません。
   実際にProduct固有の機能は、その依存を明示してProduct側に置きます。

4. **実際のアプリの開発につながる。**
   可能な限り実機と同じソースやインターフェースを使い、表示や動きは動作中のアプリの出力に基づけます。
   修正をシミュレータへ反映し、そこでの確認が実機へ載せる実装の確認として積み上がる構成にします。
   部品単体のデモや模擬入力は、その状態が分かるようにし、アプリ接続時の挙動と区別します。

5. **確かめたいことに必要な精度がある。**
   入力への反応、画面遷移、状態変化、機器間の連携を確認できることを重視します。
   時間や物理挙動などの再現は必要に応じて深め、再現範囲と実機で確認すべき範囲を明らかにします。

6. **人間とAIが同じ状態を扱える。**
   人間が見て触る操作と、AIが利用する入力・状態・ログを結び付けます。
   手で見つけた問題を同じ条件で再現し、修正後にも繰り返し確認できるようにします。

7. **日常的に使える軽さがある。**
   開く、試す、リセットする、変更を反映するまでを短くします。
   普段は部品とその反応を見渡せて、必要なときに詳しい診断へ進める構成にします。
   準備や保守の負担を、そこで得られる確認の価値に見合う範囲に収めます。

## NG例・アンチパターン

特に避けたいのは、AIがアプリの機能に適した完成度の高い画面を作り込むことで、
シミュレータの部品がそのデザインに飲み込まれることです。
そのアプリには便利でも、部品が見えなくなると、別の使い道を思いつく機会が失われます。

| NG例 | 期待する形 |
| --- | --- |
| ロータリーエンコーダーが音量調整専用の操作に変わり、汎用の回転・押下部品として見えなくなる。 | ノブの回転・押下を共通部品として表し、音量やメニューへの割り当てはProductが行う。 |
| 部品らしさを求めて円周ドラッグだけを要求し、マウス操作が難しくなる。 | 回る目盛りや指標を残し、−／＋・矢印キーなどの簡単な操作を併用する。 |
| サーボがペットの首振りアニメーションに溶け込み、軸・角度・チャンネルが見えなくなる。 | サーボ自体の表示と操作を残し、ペット全体の動きはProduct側の表現として組み合わせる。 |
| RFIDリーダーが入退室画面に置き換わり、カードをかざす操作や読取状態が隠れる。 | リーダーとカードの存在・読取状態を見せ、入退室の判定や表示をアプリに接続する。 |
| アプリの画面がブラウザ全体のデザインに溶け込み、機器のディスプレイの範囲が分からなくなる。 | ディスプレイ部品の範囲を保ち、その中にアプリの画面を表示する。 |
| Productごとに部品の外観と内部構造を作り直し、共通部品としての見覚えがなくなる。 | 共通部品の姿と基本操作を保ち、配置・設定・外側のラベルでProductを構成する。 |
| 内部コードは共通でも、名前・見た目・イベントが特定アプリの用途に結び付いている。 | 部品単体でも意味が通る姿とAPIにし、用途はProduct側で割り当てる。 |
| 単体サンプルでは部品が見えるが、Productへ組み込むと専用デザインに隠れてしまう。 | Productパネルでも部品の正体と基本操作を把握できることを確認する。 |

## 完成条件

実装・レビューでは、次を確認します。

- 元のアプリの名前や用途別ラベルを外しても、部品の正体と操作方法が分かり、別の用途を想像できる。
- マウス・キーボードで簡単に操作でき、実物の動かし方を再現する操作だけに依存しない。
- 元のProductと無関係なサンプルで、設定の異なる二つのインスタンスを並べ、独立した状態と操作を示せる。
- 共通部品をProduct adapterから切り離して読み込め、公開イベント・プロパティを確認できる。
- 実際のProductパネルでも部品の姿と基本操作を保ち、アプリへの入力と出力表示の接続を確認できる。
- Product adapterの接続確認と共通部品の確認を分け、再現した範囲と実機での未確認事項を説明できる。

完成報告には、共通部品の配置先、Product側に残した意味・接続処理、単体とProductでの確認結果を示します。
